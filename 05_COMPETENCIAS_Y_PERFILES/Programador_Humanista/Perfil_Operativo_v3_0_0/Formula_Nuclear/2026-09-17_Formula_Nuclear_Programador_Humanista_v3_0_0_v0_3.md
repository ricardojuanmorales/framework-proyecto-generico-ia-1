## 1. Propósito

Esta Fórmula Nuclear condensa la identidad normalizada del Programador Humanista después de separar su núcleo propio de responsabilidades históricamente absorbidas por el perfil piloto.

No es un inventario de capacidades ni una suma de funciones del Framework.

Debe permitir decidir:

```text
qué pertenece al PH
qué pertenece a la macroestructura
qué debe transferirse a IT o AT
qué debe permanecer como responsabilidad longitudinal
```

---

## 2. Tesis nuclear

El Programador Humanista es la lente que **convierte necesidades humanas situadas en configuraciones tecnológicas funcionales, gobernables y evolutivas**.

Su núcleo no es:

```text
programar
+ usar IA
+ diseñar experiencias
+ investigar
+ asegurar
+ documentar
```

como suma de oficios.

Su núcleo es **construir tecnología situada con responsabilidad humana**, integrando solo las capacidades necesarias para que esa construcción funcione, pueda revisarse y siga siendo gobernable.

---

## 3. Fórmula comprimida

```text
PH =
Propósito humano situado
+ Diseño computacional
+ Construcción funcional
+ Integración responsable
+ Verificación
+ Documentación viva
+ Evolución mantenible
```

Atravesado longitudinalmente por:

```text
agencia humana
+ accesibilidad
+ seguridad
+ privacidad
+ trazabilidad
+ revisión
+ transferencia reversible
```

---

## 4. Fórmula ampliada

```text
Problema complejo situado
+ necesidad de intervención tecnológica
+ propósito humano
+ requisitos y restricciones
+ diseño computacional
+ arquitectura técnica
+ construcción / integración
+ pruebas y verificación
+ seguridad, privacidad y accesibilidad
+ documentación viva
+ despliegue / operación cuando corresponda
+ mantenimiento / evolución
+ transferencia o reapertura
→ actuación tecnológica humanista
```

La secuencia no es rígidamente lineal.

Puede reabrirse cuando una prueba, riesgo, dependencia, cambio de contexto o aporte de IT/AT modifique la intervención.

---

## 5. Núcleo verbal

El PH:

```text
sitúa
→ diseña
→ construye
→ integra
→ verifica
→ documenta
→ mantiene
→ evoluciona
```

No todas las actuaciones requieren desplegar un sistema real.

Un prototipo, script, integración, interfaz, automatización o arquitectura puede ser suficiente si responde proporcionalmente al problema y deja trazabilidad adecuada.

---

## 6. Responsabilidad irreductible

La responsabilidad irreductible del PH es:

> **hacer posible una intervención tecnológica situada que pueda funcionar, comprenderse, revisarse, protegerse, mantenerse y evolucionar sin perder su relación con las personas y el contexto.**

Esta responsabilidad distingue PH de:

- IT, cuya responsabilidad distintiva es epistemológica;
- AT, cuya responsabilidad distintiva es artística situada;
- la macroestructura, que gobierna capacidades generales reutilizables.

---

## 7. Humanismo tecnológico

El adjetivo **Humanista** no significa que PH deba asumir todas las ciencias humanas, la pedagogía, el arte o la ética como dominios propios.

Significa que su construcción tecnológica conserva preguntas como:

```text
¿para quién?
¿para qué?
¿en qué contexto?
¿con qué agencia humana?
¿qué riesgos y exclusiones introduce?
¿qué debe seguir siendo revisable?
¿qué ocurre cuando falla?
¿quién puede mantenerlo o retirarlo?
```

El humanismo funciona como orientación de responsabilidad, no como expansión ilimitada del perfil.

---

## 8. Construcción funcional

"Funcional" no significa solamente que el código ejecute.

Implica una relación coherente entre:

```text
propósito
+ requisitos
+ arquitectura
+ comportamiento observable
+ condiciones de uso
+ condiciones de fallo
+ pruebas
+ documentación
```

Un artefacto que funciona una vez en condiciones no documentadas permanece exploratorio.

---

## 9. Diseño computacional

El diseño computacional es el puente entre problema y construcción.

Puede incluir:

- descomposición;
- modelado;
- arquitectura;
- interfaces;
- flujos;
- estados;
- datos;
- dependencias;
- límites de confianza;
- criterios de aceptación;
- decisiones de implementación.

No exige una tecnología específica.

```text
diseño computacional != stack
arquitectura != herramienta
```

---

## 10. Integración responsable

PH puede integrar:

```text
código
datos
APIs
servicios
modelos de IA
interfaces
repositorios
automatizaciones
infraestructura
componentes externos
```

La integración madura exige conocer:

```text
roles
dependencias
permisos
límites
fallbacks
procedencia
riesgos
puntos de revisión humana
```

Integrar no es conectar piezas hasta que "funcionen". Es gobernar las relaciones que hacen posible el sistema.

---

## 11. Verificación

PH debe distinguir:

```text
construcción
≠ verificación
```

La verificación puede incluir:

- pruebas funcionales;
- pruebas de integración;
- criterios de aceptación;
- revisión de código;
- inspección de configuraciones;
- pruebas de accesibilidad;
- revisión de seguridad;
- observabilidad básica;
- evaluación de recuperación ante fallos.

Estos rastros sostienen evidencia funcional/técnica del PH.

No sustituyen evidencia investigativa en sentido IT.

---

## 12. Documentación viva

La documentación es parte de la construcción.

Puede incluir:

```text
README
decisiones
diagramas
bitácoras
changelog
issues
pull requests
comentarios técnicos pertinentes
runbooks
registro de deuda
criterios de aceptación
límites conocidos
```

La regla es proporcionalidad:

```text
documentación suficiente para continuidad
≠ documentación máxima
```

---

## 13. Evolución mantenible

Una intervención PH madura considera que los sistemas cambian.

Debe poder responder, cuando aplique:

```text
¿cómo se actualiza?
¿cómo se observa?
¿cómo se corrige?
¿cómo se revierte?
¿cómo se retira?
¿qué deuda mantiene?
¿quién puede continuar el trabajo?
```

Mantenimiento y despliegue pertenecen a la macroestructura como capacidades generales, pero PH debe diseñar para poder invocarlas responsablemente.

---

## 14. Seguridad, privacidad y accesibilidad

Estas responsabilidades atraviesan la fórmula.

No aparecen como sumandos identitarios independientes porque:

```text
seguridad general → Framework
privacidad general → Framework
accesibilidad transversal → Framework
```

PH las especializa dentro de su construcción.

Por ello:

```text
construcción PH madura
= funcionalidad
+ responsabilidad sobre riesgos materiales de la construcción
```

Un riesgo crítico no debe compensarse con buena funcionalidad.

---

## 15. Humano-Máquina-IA

La IA no forma parte del núcleo identitario por sí sola.

Puede intervenir en:

```text
diseño
programación
revisión
pruebas
documentación
clasificación
automatización
integración
```

Regla nuclear:

> **El PH gobierna técnica y operacionalmente la integración H-M-IA dentro de su propia actuación.**

Esto requiere propósito, límites, roles, permisos, trazabilidad, revisión humana y fallback proporcional.

La IA no decide automáticamente qué construir ni qué riesgo aceptar.

---

## 16. Educación como dominio histórico/piloto prioritario

La educación permanece ligada al PH por historia y evidencia acumulada.

Pero la Fórmula Nuclear no incluye "educación" como requisito universal.

```text
construcción tecnológica humanista situada
→ identidad

educación
→ dominio histórico/piloto prioritario
```

Esto permite preservar el repositorio piloto y los casos educativos sin convertirlos en frontera identitaria.

---

## 17. Frontera con IT

PH puede producir:

```text
logs
datos operativos
pruebas
instrumentos técnicos
telemetría
artefactos
anomalías
```

IT puede convertir materiales pertinentes en parte de un proceso investigativo bajo criterios de método, evidencia, análisis e incertidumbre.

Regla:

```text
evidencia funcional PH
!= evidencia epistemológica automática
```

PH no absorbe la responsabilidad epistemológica del IT.

---

## 18. Frontera con AT

PH puede diseñar interfaces, interacción, legibilidad y accesibilidad.

AT puede trabajar percepción, imaginación, configuración sensible-simbólica-material, interpretación y transformación.

Regla:

```text
experiencia funcional PH
!= práctica artística AT
```

La colaboración puede ser intensa sin borrar fronteras.

---

## 19. Transferencia

La transferencia no forma parte de una obligación triádica universal.

PH puede:

```text
entregar
recibir
transformar
devolver
dejar pendiente
rechazar justificadamente
reabrir
```

Lo que se transfiere puede incluir:

```text
artefactos
restricciones
interfaces
datos operativos
anomalías
posibilidades técnicas
decisiones de arquitectura
necesidades de investigación
necesidades de mediación
```

La transferencia madura conserva qué cambió.

---

## 20. Caleidoscopio

PH no "produce" el Caleidoscopio por integrar funciones.

```text
PH + IT + AT != Caleidoscopio automático
```

Puede aparecer emergencia caleidoscópica cuando la construcción PH se recombina de forma trazable con otras lentes alrededor del problema y surge algo no contenido completamente en una sola de ellas.

---

## 21. Anti-fórmulas

```text
PH != código + IA + documentación
PH != educación + programación
PH != desarrollador full-stack + ética
PH != seguridad + DevSecOps + despliegue
PH != integrador obligatorio de IT y AT
PH != constructor de aplicaciones por defecto
PH != mini-Framework técnico
```

También:

```text
más herramientas != más madurez
más automatización != más agencia
más complejidad != mejor arquitectura
más documentación != más trazabilidad
```

---

## 22. Fórmula de pertenencia

Una actuación pertenece al núcleo PH cuando puede responder de forma suficiente:

```text
1. ¿Qué necesidad humana situada atiende?
2. ¿Qué intervención tecnológica hace posible?
3. ¿Cómo se diseñó y construyó?
4. ¿Cómo se verifica?
5. ¿Qué riesgos materiales introduce?
6. ¿Cómo queda documentada?
7. ¿Cómo puede mantenerse, evolucionar o retirarse?
```

No toda actuación necesita responder con la misma profundidad.

La proporcionalidad depende del riesgo, escala y contexto.

---

## 23. Fórmula de madurez

```text
Madurez PH =
coherencia entre propósito
+ arquitectura
+ construcción
+ verificación
+ responsabilidad
+ documentación
+ evolución
```

N1-N4 expresa profundidad creciente de esa integración.

No se deriva de un promedio universal ni del número de tecnologías utilizadas.

## 25. Implicaciones para la siguiente cascada

La futura Matriz de Competencias deberá derivar capacidades observables de esta fórmula sin volver a incorporar como competencias propias completas:

```text
investigación IT
práctica artística AT
seguridad general del Framework
despliegue general
mantenimiento general
diseño instruccional universal
```

Podrá incluir las capacidades PH necesarias para **invocar, integrar y responder responsablemente** a esas funciones.

Las Unidades Nucleares deberán construirse después de estabilizar competencias.

---

## 26. Criterios de reapertura

La Fórmula Nuclear PH puede reabrirse si:

- cambia la frontera identitaria del perfil;
- construcción tecnológica situada deja de explicar su responsabilidad distintiva;
- una competencia futura exige una responsabilidad irreductible no cubierta;
- la comparación PH-IT-AT revela asimetría material;
- el piloto real demuestra que la fórmula excluye prácticas PH legítimas de manera sistemática;
- cambia la Gramática Arquitectónica Común.

No se reabre por aparición de una nueva herramienta, modelo, lenguaje, stack o plataforma.

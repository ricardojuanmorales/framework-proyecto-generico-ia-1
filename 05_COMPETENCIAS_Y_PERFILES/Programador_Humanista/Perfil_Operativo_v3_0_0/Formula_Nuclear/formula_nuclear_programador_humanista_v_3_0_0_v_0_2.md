## 1. Propósito del documento

Este documento condensa la identidad funcional del **Programador Humanista v3.0.0** en una fórmula nuclear capaz de orientar competencias, unidades nucleares, aplicaciones educativas, métricas, transferencia simétrica, seguridad longitudinal y gobernanza del perfil.

La fórmula nuclear no es un lema decorativo. Es el centro de gravedad conceptual y operativo del perfil. Debe permitir decidir qué pertenece al Programador Humanista, qué queda fuera, qué requiere enlace espejo y qué debe transferirse hacia el Investigador Transdisciplinario y el Artista Transdisciplinario.

---

## 2. Fórmula nuclear breve

```text
Programador Humanista = construcción funcional + evidencia + experiencia + seguridad longitudinal + documentación viva
```

Versión expandida:

```text
Programador Humanista v3.0.0 =
crear artefactos digitales educativos, investigativos y culturales
que funcionen,
que puedan estudiarse,
que produzcan experiencia significativa,
que nazcan con seguridad y privacidad incorporadas,
y que permanezcan documentados, auditables, mantenibles y transferibles.
```

---

## 3. Núcleo verbal

El Programador Humanista v3.0.0 **traduce necesidades humanas en artefactos digitales confiables**.

Construye soluciones educativas con pensamiento computacional, inteligencia artificial, diseño instruccional, sensibilidad artística, evidencia investigativa, seguridad longitudinal y documentación viva.

Su práctica no termina cuando algo funciona. Termina provisionalmente cuando algo puede ser comprendido, revisado, usado, evaluado, mantenido, protegido y transferido.

---

## 4. Ecuación rectora

```text
PH v3.0.0 = F + E + X + S + D + G + T
```

Donde:

| Símbolo | Dimensión | Descripción |
|---|---|---|
| F | Funcionalidad | Lo construido debe operar, probarse y mantenerse. |
| E | Evidencia | Lo construido debe producir, sostener o dialogar con conocimiento verificable. |
| X | Experiencia | Lo construido debe comunicar sentido y generar interacción humana significativa. |
| S | Seguridad | Lo construido debe incorporar seguridad, privacidad y confianza desde el diseño. |
| D | Documentación | Lo construido debe dejar rastro vivo, comprensible y auditable. |
| G | Gobernanza | Lo construido debe registrar decisiones, límites, riesgos y responsabilidades. |
| T | Transferencia | Lo construido debe poder traducirse a investigación, arte, docencia y comunidad. |

## 5. Tríada constitutiva

El Programador Humanista no opera solo. Su identidad se estabiliza por transferencia simétrica con dos perfiles espejo:

```text
Programador Humanista → construye artefactos funcionales y sostenibles
Investigador Transdisciplinario → valida evidencia, método y conocimiento
Artista Transdisciplinario → transforma experiencia, expresión y sentido
```

La fórmula triádica mínima es:

```text
Construir + Conocer + Sentir
```

La fórmula triádica operativa es:

```text
Función técnica + validez investigativa + experiencia expresiva
```

La fórmula triádica ampliada para Fase 1 es:

```text
Función técnica + validez investigativa + experiencia expresiva + seguridad longitudinal + documentación viva
```

## 6. Columna de confianza

La confianza no es un atributo posterior del producto. Es una condición inicial del diseño.

El Programador Humanista v3.0.0 trabaja bajo cuatro compromisos longitudinales:

| Compromiso | Sentido operativo |
|---|---|
| Security by design | La seguridad se incorpora desde requisitos, arquitectura y diseño. |
| Security by default | Las configuraciones iniciales deben reducir exposición y riesgo. |
| SSDLC / SSDF | El ciclo de vida completo debe incluir prácticas de desarrollo seguro. |
| DevSecOps | La seguridad debe integrarse en repositorio, revisión, pruebas, CI/CD, despliegue y mantenimiento. |

La fórmula de confianza es:

```text
Confianza = seguridad por diseño + seguridad por defecto + revisión humana + evidencia + trazabilidad
```

## 7. Principio de no reducción

El Programador Humanista no debe reducirse a ninguna de estas figuras aisladas:

| Reducción incompleta | Por qué no basta |
|---|---|
| Programador técnico | Puede construir, pero no necesariamente enseñar, investigar, cuidar experiencia o documentar sentido. |
| Diseñador instruccional | Puede organizar aprendizaje, pero no necesariamente implementar, auditar o mantener artefactos digitales. |
| Investigador | Puede producir conocimiento, pero no necesariamente convertirlo en sistemas utilizables. |
| Artista digital | Puede crear experiencia, pero no necesariamente sostener seguridad, evidencia o mantenimiento. |
| Especialista en ciberseguridad | Puede proteger sistemas, pero no necesariamente articular pedagogía, investigación, arte y comunidad. |
| Usuario avanzado de IA | Puede usar herramientas, pero no necesariamente construir arquitectura, gobernanza y transferencia. |

El Programador Humanista integra esas dimensiones sin sustituir la especialización profunda de cada campo.

## 8. Definición canónica

El **Programador Humanista v3.0.0** es un perfil transdisciplinario que diseña, construye, documenta, evalúa y mantiene artefactos digitales educativos, investigativos y culturales con inteligencia artificial, seguridad longitudinal, sensibilidad humana, evidencia verificable, experiencia significativa y capacidad de transferencia.

Su práctica une:

```text
programación responsable,
investigación transdisciplinaria,
arte y experiencia,
diseño educativo,
seguridad y privacidad,
gobernanza documental,
y mantenimiento evolutivo.
```

## 10. Invariantes del perfil

Un producto pertenece al campo del Programador Humanista cuando cumple, al menos de forma inicial, estas invariantes:

| Invariante | Pregunta mínima |
|---|---|
| Funciona | ¿Hace algo útil, observable o verificable? |
| Enseña o apoya aprendizaje | ¿Tiene relación con formación, comprensión, práctica o mediación educativa? |
| Puede investigarse | ¿Produce evidencia, preguntas, datos, observaciones o trazabilidad? |
| Comunica experiencia | ¿Cuida interfaz, lenguaje, narrativa, accesibilidad o sentido? |
| Protege | ¿Considera seguridad, privacidad, datos, permisos, riesgos y configuración? |
| Documenta | ¿Deja rastro suficiente para ser revisado por otra persona? |
| Se mantiene | ¿Tiene ruta de evolución, soporte, deuda técnica o retiro? |
| Se transfiere | ¿Puede adaptarse a investigación, arte, docencia, comunidad o gestión? |

---

## 11. Criterio de pertenencia

Un artefacto, actividad o documento puede clasificarse como parte del Programador Humanista v3.0.0 si responde afirmativamente a cuatro preguntas mínimas:

```text
1. ¿Qué problema humano, educativo, investigativo o cultural atiende?
2. ¿Qué construye o hace posible técnicamente?
3. ¿Qué evidencia, experiencia o aprendizaje produce?
4. ¿Qué condiciones de seguridad, privacidad, documentación y mantenimiento exige?
```

Si no puede responder la cuarta pregunta, el producto puede ser exploratorio, pero no debe considerarse maduro.

## 12. Fórmula de madurez

La madurez del Programador Humanista no se mide solo por complejidad técnica.

```text
Madurez PH = utilidad + trazabilidad + seguridad + evidencia + experiencia + sostenibilidad
```

| Nivel | Indicador de madurez |
|---|---|
| Bajo | Funciona de forma aislada, pero no está documentado ni evaluado. |
| Inicial | Tiene propósito, documentación mínima y revisión humana básica. |
| Intermedio | Integra evidencia, seguridad inicial, transferencia y mantenimiento. |
| N3 avanzado | Articula técnica, investigación, experiencia, seguridad, gobernanza y métricas. |
| N4 emergente | Puede escalar, auditarse, desplegarse, mantenerse y transferirse a ecosistemas complejos. |

## 13. Relación con seguridad longitudinal

La seguridad forma parte del núcleo, no del perímetro.

El Programador Humanista debe reconocer que cada artefacto digital introduce alguna combinación de:

```text
datos,
usuarios,
identidades,
permisos,
dependencias,
interfaces,
modelos de IA,
infraestructura,
configuraciones,
secrets,
flujos de publicación,
y responsabilidades humanas.
```

Por eso, cada producto debe incorporar una lectura mínima de seguridad:

| Pregunta | Resultado esperado |
|---|---|
| ¿Qué puede salir mal? | Riesgos identificados. |
| ¿Qué datos o usuarios se exponen? | Clasificación básica. |
| ¿Qué configuración inicial reduce riesgo? | Seguridad por defecto. |
| ¿Qué control debe existir antes de avanzar? | Gate técnico. |
| ¿Qué queda pendiente? | Deuda o excepción documentada. |

## 15. Relación con IA

La IA no sustituye al Programador Humanista. Amplifica su capacidad de diseño, construcción, revisión, documentación y experimentación.

El uso de IA debe cumplir cuatro reglas mínimas:

| Regla | Descripción |
|---|---|
| Revisión humana | Ningún resultado crítico se acepta sin evaluación humana. |
| Trazabilidad | Las decisiones relevantes deben registrarse. |
| Contexto | El uso de IA debe responder a propósito, usuario y restricción. |
| Seguridad | Los datos, prompts, salidas, integraciones y permisos deben revisarse. |

La fórmula mínima de IA responsable es:

```text
IA útil = asistencia + revisión + contexto + límites + documentación
```

## 18. Implicaciones para métricas

Las métricas deben evaluar más que producto terminado. Deben evaluar madurez del proceso.

| Dimensión | Métrica inicial |
|---|---|
| Funcionalidad | El artefacto realiza una tarea verificable. |
| Claridad | El propósito y uso son comprensibles para otra persona. |
| Evidencia | Existe rastro de prueba, observación, dato o evaluación. |
| Experiencia | La interacción es accesible, significativa y comunicable. |
| Seguridad | Se aplicó checklist, gate o justificación de no aplicación. |
| Documentación | README, bitácora o changelog permiten continuidad. |
| Mantenimiento | Hay ruta de actualización, soporte, deuda o retiro. |
| Transferencia | Existe lectura técnica, investigativa y artística. |
| Gobernanza | Las decisiones relevantes están registradas. |

## 19. Prueba de coherencia nuclear

Antes de aceptar un producto como parte del perfil, se le aplicará una prueba breve:

```text
1. ¿Funciona?
2. ¿Sirve a un propósito humano o educativo?
3. ¿Puede producir evidencia o aprendizaje?
4. ¿Genera experiencia comprensible y significativa?
5. ¿Protege datos, usuarios, configuración y contexto?
6. ¿Está documentado para continuidad?
7. ¿Puede mantenerse o retirarse responsablemente?
8. ¿Puede transferirse a investigación, arte, docencia o comunidad?
```

Resultado posible:

```text
Apto para avanzar
Apto con observaciones
Exploratorio, no estable
Bloqueado por riesgo
No pertenece al perfil
```

## 20. Antifórmulas

Estas expresiones indican desviaciones del perfil:

| Antifórmula | Riesgo |
|---|---|
| Funciona, pero nadie sabe cómo | Fragilidad documental. |
| Funciona, pero no se puede revisar | Opacidad técnica. |
| Funciona, pero expone datos | Falla de seguridad. |
| Funciona, pero no enseña nada | Desalineación educativa. |
| Funciona, pero no produce evidencia | Debilidad investigativa. |
| Funciona, pero no comunica sentido | Pobreza experiencial. |
| Funciona, pero no se mantiene | Deuda técnica prematura. |
| Funciona, pero no se transfiere | Encierro del conocimiento. |

La pregunta crítica no es solo si algo funciona. La pregunta completa es:

```text
¿Funciona de forma humana, segura, documentada, evaluable, mantenible y transferible?
```

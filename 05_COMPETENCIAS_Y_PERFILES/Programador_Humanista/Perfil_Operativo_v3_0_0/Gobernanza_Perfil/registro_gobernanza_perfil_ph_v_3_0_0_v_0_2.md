## 1. Propósito del documento

Este documento establece el **Registro de Gobernanza del Perfil Programador Humanista v3.0.0**.

Su función es registrar decisiones, criterios, riesgos, excepciones, estados de aprobación, cambios de versión, responsabilidades, gates, enlaces espejo y condiciones de avance durante la Fase 1.

La gobernanza no se entiende como freno administrativo. Se entiende como memoria operativa, brújula ética y sistema de trazabilidad para evitar que los productos del perfil se vuelvan piezas sueltas sin dueño, sin ruta y sin revisión.

---

## 2. Tesis de gobernanza

El Programador Humanista produce artefactos, documentos, aplicaciones, matrices y experiencias que deben poder ser comprendidas, evaluadas, protegidas, mantenidas y transferidas.

Por tanto, cada decisión relevante debe responder:

```text
Qué se decidió
Por qué se decidió
Dónde vive la evidencia
Qué riesgo introduce o reduce
Qué producto afecta
Qué enlace espejo conecta
Qué revisión futura requiere
```

La gobernanza del perfil opera como una bitácora de navegación. No sustituye la creación, pero impide que la creación pierda coordenadas.

## 4. Principios de gobernanza

| Principio | Descripción operativa |
|---|---|
| Trazabilidad | Toda decisión importante debe poder rastrearse. |
| Proporcionalidad | La documentación debe ser suficiente, no ornamental. |
| Centralización con espejos | El perfil conserva visión central y enlaza detalles técnicos. |
| Seguridad longitudinal | La seguridad se gobierna desde el inicio y durante todo el ciclo. |
| Revisión humana | Las decisiones críticas requieren juicio humano explícito. |
| Transferencia simétrica | Cada producto debe dialogar con técnica, investigación, arte y confianza. |
| Versionado responsable | Las versiones previas no se borran sin criterio de archivo. |
| Excepciones documentadas | Lo que no se hace debe explicarse, no evaporarse. |
| Cierre verificable | Ninguna fase se cierra solo por entusiasmo. Debe existir evidencia. |

## 12. Protocolo mínimo de cambio

Todo cambio sustantivo debe seguir esta secuencia:

```text
1. Identificar documento afectado
2. Determinar si el cambio es menor, sustantivo o estructural
3. Registrar decisión o excepción si aplica
4. Actualizar versión o mantener subversión según alcance
5. Revisar enlaces espejo afectados
6. Revisar impacto en seguridad longitudinal
7. Revisar impacto en transferencia triádica
8. Actualizar changelog
9. Registrar commit cuando corresponda
```

### 12.1 Tipos de cambio

| Tipo | Descripción | Requiere registro |
|---|---|---|
| Editorial menor | Ortografía, formato, claridad local | Changelog opcional |
| Sustantivo | Cambia criterio, matriz, definición o secuencia | Sí |
| Arquitectónico | Cambia estructura, ubicación, dependencia o estrategia | Sí, con decisión |
| Seguridad | Cambia controles, gates, riesgos o excepciones | Sí, con revisión |
| Transferencia | Cambia relación PH-IT-AT o estado de transferencia | Sí |
| Archivo o cierre | Mueve documentos a histórico o declara versión cerrada | Sí |

Cuando un control, gate, documento o evidencia no aplique o se aplace, se debe registrar:

## 14. Gobernanza de seguridad longitudinal

La seguridad longitudinal se gobierna mediante cuatro mecanismos:

| Mecanismo | Función |
|---|---|
| Matriz de Seguridad Longitudinal | Define principios, checklist, gates y evidencias |
| Métricas N3/N4 | Evalúa seguridad como dimensión no compensable |
| Enlaces Espejo | Conecta seguridad con cartapacios técnicos especializados |
| Registro de Gobernanza | Documenta decisiones, riesgos, excepciones y cambios |

### 14.1 Regla de seguridad no compensable

Un producto no puede declararse maduro si tiene riesgo alto de seguridad, privacidad, datos, secretos o exposición sin mitigación documentada, aunque tenga buena funcionalidad, experiencia o documentación.

### 15.1 Estados válidos de transferencia

```text
Transferencia completa
Transferencia parcial
Transferencia pendiente
Transferencia no aplicable
Transferencia bloqueada
```

Todo producto rector debe declarar o permitir inferir su estado de transferencia.

## 16. Gobernanza de enlaces espejo

Los enlaces espejo deben revisarse cuando:

1. cambia la versión de un documento rector;
2. cambia la ubicación de un documento técnico;
3. se crea una matriz nueva;
4. se cierra una fase;
5. se identifica un riesgo de seguridad;
6. se archiva una versión;
7. se prepara transferencia hacia otro perfil, curso, proyecto o comunidad.

### 16.1 Estados válidos de enlace espejo

```text
Activo
Pendiente
Parcial
En revisión
Obsoleto
Archivado
Bloqueado
```

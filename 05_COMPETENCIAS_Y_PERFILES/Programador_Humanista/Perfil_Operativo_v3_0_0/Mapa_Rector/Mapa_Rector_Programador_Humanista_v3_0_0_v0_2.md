## 1. Propósito del documento

Este documento convierte el alcance operativo actualizado del **Programador Humanista v3.0.0** en un mapa rector de trabajo.

Su función es ordenar componentes, dependencias, productos, secuencias, criterios de evaluación, riesgos, enlaces espejo, transferencia simétrica triádica y seguridad longitudinal para guiar la Fase 1 sin modificar la estructura de cartapacios.

El mapa rector v0.2 actualiza la versión anterior para evitar un error en cascada: la seguridad no se añadirá como capa tardía de auditoría, sino como principio arquitectónico desde el inicio y como práctica longitudinal durante todo el ciclo de vida del trabajo.

---

## 2. Tesis rectora

El Programador Humanista v3.0.0 es un perfil transdisciplinario que convierte necesidades educativas, investigativas, comunitarias o institucionales en artefactos digitales funcionales, documentados, evaluables, expresivos, seguros y sostenibles.

Su identidad se organiza alrededor de dos ejes inseparables:

```text
Eje triádico:
Programador Humanista → construcción funcional, arquitectura técnica y sostenibilidad
Investigador Transdisciplinario → evidencia, método, trazabilidad y producción de conocimiento
Artista Transdisciplinario → experiencia, lenguaje, percepción, mediación y sentido

Eje de confianza:
Security by design → seguridad incorporada desde la concepción
Security by default → configuraciones iniciales seguras y mínimas
SSDLC / SSDF → ciclo de vida de desarrollo seguro
DevSecOps → seguridad integrada al flujo técnico, revisión, despliegue y evolución
```

La Fase 1 debe producir una arquitectura suficientemente clara para que cada producto posterior pueda responder seis preguntas:

1. ¿Qué se construye y cómo se mantiene?
2. ¿Qué evidencia produce o qué pregunta permite estudiar?
3. ¿Qué experiencia genera y cómo comunica sentido?
4. ¿Qué riesgos introduce y cómo se mitigan?
5. ¿Qué controles mínimos exige antes de avanzar?
6. ¿Qué documentación permite auditar su evolución?

## 3. Principios rectores actualizados

### 3.1 Humanismo tecnológico

La tecnología se entiende como medio de ampliación humana, no como sustitución del juicio, la relación educativa ni la responsabilidad ética.

### 3.2 Seguridad y confianza desde el diseño

Todo artefacto debe diseñarse con conciencia de riesgo desde su concepción. Esto incluye datos, usuarios, permisos, dependencias, APIs, secretos, accesibilidad, privacidad, interfaz, despliegue y mantenimiento.

### 3.3 Seguridad por defecto

La configuración inicial de cualquier prototipo, aplicación, flujo o repositorio debe ser la opción más segura razonable, no la más rápida ni la más cómoda.

### 3.4 Funcionalidad verificable

Todo artefacto debe poder probarse, documentarse, corregirse y mantenerse. La funcionalidad sin trazabilidad no es madurez técnica.

### 3.5 SSDLC y DevSecOps como práctica longitudinal

La seguridad debe aparecer en requisitos, diseño, implementación, revisión, pruebas, despliegue, observabilidad, incidentes, mantenimiento y retiro.

### 3.6 Transferencia simétrica triádica

Cada componente del Programador Humanista debe tener una posible traducción investigativa y artística, aun cuando esa traducción sea parcial o pendiente.

### 3.7 Documentación viva

Cada avance debe dejar rastro: bitácora, decisión, mapa, README, changelog, checklist, gate, criterio de evaluación o enlace espejo.

### 3.8 Gobernanza mínima desde el inicio

No se espera gobernanza completa en Fase 1, pero sí registro claro de decisiones, límites, riesgos, excepciones y controles mínimos.

### 3.9 Progresión N3 → N4

El perfil debe sostener desempeño N3 avanzado y preparar condiciones para N4, especialmente en integración técnica, investigación, agentes, auditoría, seguridad, despliegue, documentación humana y transferencia.

## 7. Marcos, prácticas y herramientas de referencia

Los siguientes marcos, prácticas y herramientas no se tratan como decoración técnica. Funcionan como brújulas de diseño, evaluación y documentación.

| Marco, práctica o herramienta | Función en el PH v3.0.0 | Evidencia mínima | Cartapacio espejo |
|---|---|---|---|
| Security by design | Incorporar controles desde requisitos y arquitectura | decisiones de diseño y riesgos documentados | `04`, `16` |
| Security by default | Reducir exposición inicial mediante configuración segura | plantilla base segura y checklist de configuración | `07`, `16`, `19` |
| OWASP Top 10 | Identificar riesgos críticos en aplicaciones web | checklist OWASP por aplicación | `15`, `16` |
| OWASP Proactive Controls | Traducir riesgos en prácticas positivas de desarrollo seguro | checklist de controles proactivos | `10`, `16` |
| MITRE ATT&CK defensivo | Mapear amenazas, tácticas y mitigaciones desde perspectiva defensiva | matriz de amenazas y mitigaciones | `04`, `16`, `15` |
| SSDF / SSDLC | Integrar seguridad durante todo el ciclo de vida | gates por fase | `03`, `15`, `16`, `20` |
| DevSecOps | Integrar seguridad en repositorio, PR, CI/CD y despliegue | evidencia de revisión, escaneo y aprobación | `10`, `15`, `19` |
| Codificación segura | Evitar errores comunes por lenguaje o stack | checklist por stack | `10`, `16` |
| Snyk o equivalente | Revisar dependencias, código, contenedores o configuración | reporte o evidencia de revisión | `10`, `15`, `16`, `19` |
| Laravel u otro stack web | Aplicar prácticas específicas del framework adoptado | checklist del stack y revisión de configuración | `10`, `16`, `19` |

### 7.1 Regla de neutralidad instrumental

El mapa no obliga a usar una herramienta única. Snyk, Laravel u otros stacks se entienden como ejemplos o posibilidades de implementación. La obligación rectoral es mantener evidencia de revisión, seguridad por diseño, seguridad por defecto y trazabilidad.

### 7.2 Regla de uso defensivo

Los marcos de amenazas solo se usarán para defensa, evaluación, documentación, mitigación y educación responsable. No se usarán para crear instrucciones ofensivas, explotación no autorizada o evasión de controles.

## 8. Gates técnicos mínimos

Los gates técnicos son compuertas de avance. No buscan burocratizar el trabajo, sino evitar que un prototipo inseguro se disfrace de producto listo.

| Gate | Nombre | Pregunta de control | Evidencia mínima | Estado posible |
|---|---|---|---|---|
| G0 | Contexto y datos | ¿Qué datos, usuarios y riesgos toca el producto? | ficha de contexto | pendiente, aprobado, no aplica |
| G1 | Diseño seguro | ¿El diseño incluye controles desde el inicio? | decisiones de arquitectura y riesgos | pendiente, aprobado, no aplica |
| G2 | Codificación segura | ¿El código evita prácticas inseguras conocidas? | checklist por lenguaje o stack | pendiente, aprobado, no aplica |
| G3 | Dependencias y secretos | ¿Las dependencias, secretos y configuraciones fueron revisadas? | reporte o revisión manual | pendiente, aprobado, no aplica |
| G4 | Revisión y pruebas | ¿Hay revisión humana y pruebas mínimas? | PR, code review o bitácora de revisión | pendiente, aprobado, no aplica |
| G5 | Despliegue seguro | ¿El despliegue usa configuración segura por defecto? | checklist de despliegue y rollback | pendiente, aprobado, no aplica |
| G6 | Observabilidad y respuesta | ¿Existe ruta de monitoreo e incidentes? | runbook o protocolo mínimo | pendiente, aprobado, no aplica |
| G7 | Transferencia y documentación | ¿La decisión quedó documentada para la tríada? | bitácora y matriz PH-IT-AT | pendiente, aprobado, no aplica |

### 8.1 Estados de gate

```text
Pendiente → requiere atención antes de avanzar
Aprobado → cumple criterio mínimo
Aprobado con observaciones → puede avanzar con deuda documentada
No aplica → no corresponde al producto o fase
Bloqueado → no debe avanzar sin revisión
```

## 10. Transferencia simétrica triádica con seguridad integrada

La transferencia triádica no es un apéndice. Es una regla de diseño.

Cada producto debe poder leerse en cuatro capas:

| Capa | Pregunta | Evidencia mínima |
|---|---|---|
| Técnica | ¿Qué se construye y cómo se mantiene? | arquitectura, repositorio, código, README, pruebas, mantenimiento |
| Investigativa | ¿Qué evidencia produce o qué pregunta permite estudiar? | corpus, instrumentos, bitácoras, métricas, análisis, trazabilidad |
| Artística | ¿Qué experiencia genera y cómo comunica sentido? | narrativa, interfaz, visualización, mediación, accesibilidad expresiva |
| Seguridad y confianza | ¿Qué riesgos controla y qué condiciones exige? | matriz de riesgos, checklist, gate, revisión humana |

### 10.1 Traducción por componente

| Componente PH | Traducción IT | Traducción AT | Traducción seguridad/confianza |
|---|---|---|---|
| Aplicación educativa | Intervención estudiable, generador de evidencia | Experiencia interactiva, narrativa o multimodal | análisis de datos, privacidad, accesibilidad y riesgos web |
| Repositorio técnico | Archivo metodológico y trazable | Archivo creativo del proceso | control de secretos, ramas, revisiones y dependencias |
| Flujo de IA | Procedimiento auditable | Motor de exploración expresiva | revisión humana, límites, datos y trazabilidad de prompts |
| Métrica técnica | Indicador de calidad o confiabilidad | Indicador de experiencia y participación | indicador de riesgo, cumplimiento y gate |
| Prototipo | Piloto de investigación | Boceto expandido o interfaz pública | estado de seguridad y límites de uso |
| Documentación viva | Evidencia de decisiones y cambios | Memoria creativa y mediación cultural | registro de riesgos, excepciones, incidentes y revisiones |

### 10.2 Estados de transferencia

Todo producto se clasificará en una de cuatro categorías:

```text
Transferencia completa
Transferencia parcial
Transferencia pendiente
Transferencia no aplicable
```

### 10.3 Criterio de compatibilidad mínima

Un producto puede avanzar aunque no tenga transferencia completa, pero debe declarar su estado de transferencia y explicar qué falta para completarla.
